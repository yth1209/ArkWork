# ArkWork 제품 상세 명세

상태: 설계 제안. UI 데모 이후 실사용 MVP의 기준이며 구현 완료를 뜻하지 않는다.

## 1. 성공하는 사용자 경험

사용자가 GitHub 저장소를 연결하고 “검색 결과를 상태별로 필터링하고 싶다”라고 요청한다. ArkWork는 현재 코드를 확인하고 완료 조건을 정리한다. 큰 변경이면 명세 PR을 먼저 제안한다. 승인된 범위에서 구현을 실행하고 브라우저 동작과 테스트 증거를 연결한 구현 PR을 만든다. 사용자는 결과 화면 또는 GitHub에서 수정 요청을 남긴다. ArkWork가 해당 요청을 반영하고 최신 변경을 다시 검증한다. 병합은 사람이 결정한다.

사용자가 “이 패턴을 다음 작업에도 적용해 달라”라고 남겼다면, 이번 코드 수정과 별개로 조직 규칙 후보를 기록한다. 반복되거나 명확히 합의된 규칙만 평가를 거쳐 Skill 개선 PR로 제안한다.

## 2. 사용자와 권한

| 역할 | 권한 |
| --- | --- |
| 소유자 | 저장소 연결, 실행 정책·예산 설정, 멤버 관리, 배포 승인 |
| 유지관리자 | 명세 승인, 작업 실행·취소, 리뷰 대응 승인, Skill 개선 검토 |
| 참여자 | 요구사항 제출, 결과와 증거 확인, 피드백 작성 |
| 열람자 | 접근 가능한 작업·명세·결과 조회 |

개인 MVP에서는 소유자 한 명으로 시작한다. 조직 역할은 후속 단계다. 앱 권한이 GitHub 권한을 대체하지 않는다. 병합하려면 실제 GitHub 권한과 브랜치 보호 조건도 충족해야 한다.

## 3. 사용자 흐름

### 저장소 연결

GitHub App으로 선택한 저장소만 연결한다. 저장소와 기본 브랜치, 최근 커밋, 실행 가능 도구와 검증 명령을 확인한다. 사용자 승인 없이 빈 저장소를 초기화하지 않는다. 빈 저장소는 초기 명세 작업은 가능하지만 구현 전에 기준 브랜치를 만드는 별도 승인이 필요하다.

초기 버전은 프로젝트당 저장소 하나다. 이미 열려 있는 관련 PR과 작업을 표시해 중복 작업을 줄인다. 연결에 실패하면 권한 없음, 네트워크 실패, 설치 해제 등을 구분해 복구 방법을 표시한다.

### 요구사항 입력과 분류

- 앱 입력은 제목 1~120자, 요구사항 10~10,000자, 선택적 완료 조건과 첨부 증거로 구성한다. 현재 데모의 2,000자 제한은 실서비스 전환 시 바꾼다.
- GitHub Issue도 입력으로 수집한다. 본문과 코멘트를 같이 읽고, 제목만으로 실행하지 않는다.
- 분류 결과는 `ready_to_implement`, `ready_to_spec`, `needs_info`, `deferred` 중 하나다. 이유, 관련 코드, 필요한 다음 행동을 표시한다.
- `needs_info`는 꼭 필요한 질문만 요청하고 답변 도착 시 다시 분류한다. `deferred`는 보류 이유와 재검토 조건을 기록한다.
- 명세 단계는 분석만 수행하며 저장소 외부 작업이나 제품 구현을 시작하지 않는다.

### 명세와 실행 승인

큰 변경, 데이터 마이그레이션, 권한·외부 서비스 변경은 제품·기술 명세 PR을 먼저 작성한다. 화면에서 사용자 행동, 완료 기준, 제외 범위, 검증 방법, 실행 예산을 보여 준다. 명세 PR이 승인되어 병합된 뒤 해당 명세 커밋을 고정한다.

작고 명확한 변경은 유지관리자가 구조화된 작업 계획을 승인하면 명세 PR을 생략할 수 있다. 생략해도 완료 기준, 범위와 계획 버전을 보존한다. 첫 MVP는 모든 실제 구현에 명시적 실행 승인을 요구한다. 이후에만 정책 기반 자동 실행을 추가한다.

### 구현과 검증

에이전트는 작업별 격리 환경과 브랜치에서 실행한다. 진행 화면은 실제 서버 이벤트를 표시하며 브라우저 타이머로 실서비스 상태를 흉내 내지 않는다. 단계별 로그 요약, 경과 시간, 사용량과 차단 원인을 확인할 수 있다.

지원되는 변경은 빌드·타입 검사·관련 테스트 및 주요 사용자 흐름을 검증한다. 요구사항별로 `passed`, `failed`, `blocked`, `not_run`, `skipped`를 표시한다. 테스트 0개 실행을 통과로 표시하지 않는다. 사용자 흐름 증거에는 대상 커밋, 실행 환경, 캡처 시점과 결과를 붙인다.

실패한 검증은 원인을 조사하고 한도 내에서 수정한다. 소스 결함과 환경 장애를 구분한다. 필수 검증이 실패하거나 실행되지 않았으면 준비 완료 상태로 표시하지 않는다. 진단용 draft PR은 만들 수 있으나 차단 사유를 명시한다.

### 결과 검토와 수정 요청

결과 화면은 요구사항별 충족 여부, diff 요약, PR 링크, 테스트 결과, 화면 증거, 남은 제약과 비용을 보여 준다. 스크린샷은 실제 접속 가능한 미리보기와 다른 항목이다. 외부 주소가 없다면 “화면 캡처만 제공”이라고 표시한다.

사용자는 앱에서 GitHub 코멘트를 작성하거나 GitHub에서 직접 리뷰한다. 일반 코멘트는 자동 코드 실행의 승인이 아니다. 첫 MVP는 확인된 유지관리자의 `changes requested` 리뷰 또는 명시적 ArkWork 수정 요청을 수집하고, 작업 화면에서 수정 계획을 승인한 뒤 실행한다. 후속 정책으로 같은 승인 범위 안의 수정 자동 실행을 선택할 수 있다.

리뷰 대상 SHA와 최신 head가 다르면 예전 의견을 그대로 적용하지 않고 위치와 의도를 재확인한다. 변경 후 최신 SHA에 대한 검증과 리뷰를 다시 수행한다. 사용자가 요청하지 않은 기능 추가는 별도 작업으로 분리한다.

### 병합과 배포

기본값은 사람이 GitHub에서 병합한다. 앱의 병합 기능은 GitHub 권한, 최신 head, 필수 checks와 리뷰 조건을 재검증하고 명시적 승인을 받은 경우에만 수행한다. AI의 `APPROVE` 결과는 사람의 승인이나 병합 허가가 아니다.

배포는 병합과 독립적이다. 초기에는 연결된 테스트용 호스팅 환경으로 한정한다. 배포 대상과 공개 범위, 유지 기간, 비용을 안내한 뒤 승인받는다. 백엔드 배포는 후속 범위이고, CI 머신에 서버를 띄운 것만으로 공개 링크를 표시하지 않는다.

## 4. 화면 구성

| 화면 | 주요 정보와 동작 | 빈 상태·실패 상태 |
| --- | --- | --- |
| 프로젝트 연결 | 저장소, 브랜치, 권한, 검증 명령 | 빈 저장소, 접근 거부, 연결 해제 |
| 새 작업 | 요구사항, 완료 기준, 예산, 분류 결과 | 입력 오류, 지원 범위 밖, 추가 질문 |
| 작업 목록 | 상태, 프로젝트, 최근 이벤트, 비용 | 작업 없음, 로드 실패, 연결 재시도 |
| 작업 상세 | 명세, 단계, 로그, 승인, 취소·재시도 | 실행 대기, 오류, heartbeat 손실 |
| 결과 검토 | PR, 기준별 증거, 미리보기 상태, 변경 요청 | 검사 실패, PR 게시 실패, 주소 없음 |
| 피드백함 | 원 코멘트, 수정 상태, 학습 후보 | 중복, 모호함, 권한 없는 요청 |
| Skill 변경 | 규칙 diff, 출처, 평가, 적용 버전, PR | 근거 부족, 평가 실패, 기각, 되돌림 |
| 설정 | 연결, 예산, 허용 도메인, 자동화 범위 | 자격 증명 누락, 정책 충돌 |

모바일에서는 읽기·승인·피드백이 우선이다. 상세 diff는 파일 선택과 접기 기능으로 제공하고 GitHub 원문으로 이동할 수 있게 한다. 키보드 접근, 상태의 텍스트 표기와 진행 알림을 제공한다.

## 5. 상태와 사용자 제어

작업 상태: `received`, `triaging`, `needs_info`, `deferred`, `specifying`, `awaiting_spec_approval`, `awaiting_run_approval`, `queued`, `running`, `verifying`, `review_ready`, `changes_requested`, `awaiting_revision_approval`, `revising`, `blocked`, `failed`, `cancelling`, `cancelled`, `merged`, `closed`.

- `review_ready`는 최신 head의 필수 검증과 PR 게시가 완료된 상태다.
- 취소 요청은 먼저 `cancelling`이며 실제 실행 중단이 확인되면 `cancelled`다. 이미 생성된 PR은 별도로 남는다.
- 재시도는 새로운 attempt를 만든다. 완료된 결과나 과거 로그를 덮어쓰지 않는다.
- 병합된 작업은 완료 결과를 보존하며 후속 문제는 연결된 새 작업으로 만든다.
- 실행 환경 또는 공급자 장애는 `blocked`와 원인을 표시한다. 사용자의 제품 요구사항 결함으로 표현하지 않는다.

## 6. 실사용 MVP 수용 기준

| ID | 검증 시나리오 | 통과 조건 |
| --- | --- | --- |
| AC-01 | 동일 요청 중복 전송 | 같은 idempotency key로 작업이 한 개만 생성됨 |
| AC-02 | GitHub webhook 중복·역순 전송 | 이벤트 중복 실행 없음, 최신 상태 유지 |
| AC-03 | 모호한 요구사항 제출 | 필요한 질문을 표시하고 유료 구현을 시작하지 않음 |
| AC-04 | 승인된 기능 실행 | 고정된 명세·기준 SHA로 브랜치 생성, main 직접 변경 없음 |
| AC-05 | 필수 테스트 실패 | review_ready가 되지 않고 실패 증거가 보존됨 |
| AC-06 | 유지관리자 수정 요청 | 코멘트→수정 계획→승인→새 SHA→재검증 이력 연결 |
| AC-07 | 권한 없는 코멘트의 실행 지시 | 코드 실행과 권한 확대가 발생하지 않음 |
| AC-08 | 실행 중 취소·worker 종료 | 취소 상태 정확, lease 만료 후 중복 게시 없음 |
| AC-09 | 예산 한도 도달 | 추가 공급자 호출 중단, 비용과 종료 원인 표시 |
| AC-10 | 모바일·다른 브라우저 접속 | 인증된 동일 사용자가 서버의 같은 작업을 조회 |
| AC-11 | 외부 미리보기 미설정 | 접속 링크를 꾸며내지 않고 캡처만 표시 |
| AC-12 | Skill 개선 승인 | 별도 PR 병합 뒤에만 새 버전이 다음 실행에 적용됨 |
| AC-13 | 오래된 SHA의 리뷰·병합 요청 | 최신 head와 불일치하면 게시·병합 중단 |
| AC-14 | PR 생성 API 장애 | 재시도 후 PR 한 개만 생성되고 준비 상태가 복구됨 |

## 7. 지표

최초 결과까지의 시간, 첫 PR의 사람 승인율, 수정 회수, 검증 실행률, 작업당 추론·환경 비용, 취소 후 추가 비용, 중복 실행·게시 건수, 리뷰 오탐률, Skill 개선 전후 평가 결과를 측정한다. 초기 pilot에서 기준선을 측정하며 근거 없는 성능·가격 목표를 판매 약속으로 사용하지 않는다.
